# Porting TachiyomiAZ to iOS

Status as of 2026-08-17. This is the port of the Android app onto shared KMP code, not the
Aidoku-based `tachiyomiazios` app — that one is a separate application that happens to read
manga. The goal here is one codebase where the rules live in `:core-domain` and both apps
obey them.

## What runs today

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21
./gradlew :shared-ios:assembleTachiyomiKitDebugXCFramework
cd iosApp && xcodegen generate
xcodebuild -project TachiyomiAZ.xcodeproj -scheme TachiyomiAZ \
  -sdk iphonesimulator -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build
```

Verified on the simulator: the app launches, opens a real SQLite database in Application
Support, and renders a library from it. `sqlite3` on the resulting file shows the full
schema — `mangas`, `chapters`, `categories`, `history`, `manga_sync`, `mangas_categories`,
`merged`, `search_metadata`, `search_tags`, `search_titles` — created by `Database.Schema`
from the same `.sq` files the Android app compiles.

Writing works through the same path: `--seed-sample-library` inserts rows via the shared
`insertManga`, and they come back out through `getLibraryMangas()`.

```bash
xcrun simctl launch booted eu.kanade.tachiyomi.az.ios --seed-sample-library
```

## Layout

| Piece | What it is |
|---|---|
| `:core-model`, `:core-database`, `:core-domain` | shared, unchanged by the port |
| `:shared-ios` | umbrella module; produces `TachiyomiKit.xcframework` |
| `iosApp/` | SwiftUI app, project generated by XcodeGen from `project.yml` |

SwiftUI rather than UIKit: the navigation is the part that has to feel like Android, and a
drawer plus bottom tabs is the same either way. SwiftUI gets there in far less code, and
nothing here is hard to move later.

`IosDatabaseHandler` is the iOS implementation of `DatabaseHandler`. Because every query is
a default method on the mixins in `:core-database`, implementing `DbProvider` is genuinely
all it takes to make the whole shared query surface callable from Swift.

## Traps already paid for

**`NativeSqliteDriver` takes a bare file name.** Passing a path throws
`IllegalArgumentException: ... contains a path separator`, and since `IosDatabaseFactory` is
not `@Throws`, that does not reach Swift as an error — it terminates the process while
printing a stack trace, which presents as a white screen and a live pid. `createDriver` now
takes `directoryPath` separately so the shape of the API prevents it.

**Do not name a Kotlin type after the framework.** An `object TachiyomiKit` inside
`TachiyomiKit.xcframework` shadows the module in Swift, so `TachiyomiKit.Category` resolves
to a member of the object and every name needing qualification becomes unreferenceable. It
is `SharedCore` now.

**`Category` is ambiguous in Swift** against another module in scope; `iosApp` aliases it
once as `MangaCategory`.

**A Kotlin/Native module with no sources is `NO-SOURCE`,** so its framework link tasks skip
and Gradle still reports success. An empty umbrella module produces no XCFramework and no
error. `SharedCore.kt` is what keeps `:shared-ios` non-empty and is load-bearing.

## Not done

Everything below the library screen. Named honestly rather than stubbed:

- **Fetching a repository from iOS.** The decoder is shared now (see below); what iOS still lacks
  is the HTTP call that hands it bytes.
- **Sources.** The big one. Android loads extensions as APKs, which iOS cannot do. The
  `tachiyomiazios` repo solves this with a bundled OpenJDK Mobile *Zero* interpreter running
  Tachiyomi extension JARs, plus an Android-compatibility shim layer — see its
  `Vendor/OpenJDK/README.md` and `Runtime/`. That runtime is reusable here and is the
  intended route, but it is a substantial piece of work: the binaries are not checked in and
  are produced by a pinned build script. Until it lands, nothing can populate the library
  the normal way.
- **Reader, downloads, tracking, updates, history screens.** `HistoryQueries` and the library
  update rules are already shared; the screens are not built.
- **Cover art.** Needs the source layer.
- **Backup restore on iOS.** The format models and merge rules are already shared and tested,
  so this is closer than it looks — it needs a file picker and the decode path wired up. This
  is the demonstration worth having: same schema, same `@ProtoNumber` wire format, no
  conversion layer.
- **Swift concurrency boundary.** `suspend` functions currently surface as completion
  handlers and `Flow` needs a wrapper. SKIE or KMP-NativeCoroutines belongs in `:shared-ios`
  before much more Swift is written against `DatabaseHandler`.

Out of scope by decision: nhentai/exhentai support and legacy backup formats.

## Extension repositories

The index models and the store decoder both live in `:core-domain` and are used by `:app` and iOS
alike -- `ExtensionStoreModels.kt` and `ExtensionStoreDecoder.kt`. They were *moved* out of `:app`,
not rewritten: a second decoder means the two apps can disagree about what a repository contains,
which is the class of bug the shared modules exist to prevent. Only one line had to change to make
the decoder portable -- `okio.use` instead of `kotlin.io.use`, since the latter is for
`java.io.Closeable` and does not exist in common code.

Format is decided by reading the content, never the URL. An index may be served under any file
name and any extension, so the name promises nothing. Verified against the real keiyoushi
repository: `index.pb` is gzipped protobuf and decodes to 1368 extensions.

The legacy flat-array index stays in `:app`. It describes APK extensions, which only Android can
load; this port uses JAR extensions exclusively. Note that keiyoushi's `index.min.json` is that
legacy format and is now just an "Outdated App" stub -- use its `index.pb`.
